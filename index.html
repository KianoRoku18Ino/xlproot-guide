A field guide, not a script

A full Linux desktop, running inside your Android phone.

XoDos-Ark runs a real Linux distro — desktop environment included — inside a PRoot container on Android. No laptop required for coursework, dev tools, or a proper terminal. This guide covers the prerequisites, the install, a real conflict with banking apps that nobody warns you about, and the fixes that actually work.

THE ARCHITECTURE

What you're actually building

Every layer sits on top of the one below it. If something breaks, knowing which layer it broke in is most of the diagnosis.

L0
Android (your phone's actual OS)
Hardware, kernel, Android's own process management
L1
XoDos-Ark + PRoot
Runs a Linux filesystem in userspace — not a VM, not root access
L2
Distro (e.g. Debian)
The actual Linux userland — package manager, libraries, shell
L3
Desktop environment (e.g. XFCE4)
Window manager, panel, file manager
L4
Display server (e.g. X11 via Termux-X11)
Actually draws the desktop to your screen
L5
Your apps
VS Code, browsers, whatever coursework needs

This stack is why "it's not working" is never a full bug report — the fix at L4 (display) looks nothing like the fix at L2 (package manager). Say which layer you're on when you ask for help.

L1 — BEFORE YOU INSTALL ANYTHING

Prerequisites

Most failed installs trace back to skipping one of the two settings below — not a bad download, not a bad guide.

Device check

  • 64-bit (arm64) required. XoDos-Ark does not run on 32-bit-only devices. Nearly every phone from the last several years qualifies.
  • ~4GB free storage minimum before you start.
  • Stable Wi-Fi — the initial distro download is large.

Example: Snapdragon 7 Gen 3, Adreno 720, 8GB RAM — check yours under Settings → About Phone, or install a free app like CPU-Z or Device Info HW if you're not sure. Don't guess.

Two one-time Android settings

These apply no matter what device or distro you choose — they're Android-level, not XoDos-Ark-specific.

1 · Disable the Phantom Process Killer
Settings → About Phone → tap Build Number 7×
Settings → Developer Options → "Disable child process restrictions"

Since Android 12, the OS kills an app's child processes once too many are running — even with free RAM available. Installing packages spawns a new process per operation, so apt/dnf/pacman installs can get silently killed halfway through without this toggle. This affects this whole category of app (Termux, Andronix, Debian NoRoot, etc.), not just XoDos-Ark.

It resets automatically if Developer Options ever gets toggled off — including by a banking app that forces it off (see the next section) — and back on. Re-enable it each time that happens, before your next install session.

2 · Grant "All Files Access"
Settings → Apps → XoDos-Ark → Permissions → Files and media → Allow management of all files

Without this, tools inside the container can't see Android's storage folders at all. It looks like "no phone storage support" — it's actually just a missing permission.

Get the current build

Don't trust a version number pinned in any guide — including this one. XoDos-Ark ships new releases frequently. Always check the releases page directly:

L2 — THE PART NOBODY WARNS YOU ABOUT

Developer Options vs. your banking app

Turning on Developer Options is required for XoDos-Ark. It's also one of the exact signals your banking, government, or e-wallet apps check for before they'll let you in.

The conflict

Many banking, government, and e-wallet apps refuse to open — or quietly disable sensitive features — the moment they detect Developer Options, USB Debugging, or an active Accessibility Service. This isn't a XoDos-Ark bug. It's a deliberate anti-tampering check built into those apps, and it has nothing to do with whether you're actually doing anything malicious.

That leaves you with a real, recurring problem: you need Developer Options on for your dev environment, and off for your banking app — and manually flipping it back and forth in Settings every single time gets old fast.

Three apps solve this together, and it's worth understanding what each one actually does before you install them:

AppRole
Shizuku or BreventGives a helper app elevated access to system settings, through a one-time ADB-based authorization — without rooting your phone.
GetoThe app you actually use day to day. Once it has permission (granted through Shizuku or Brevent), Geto can flip Developer Options / USB Debugging / Accessibility off automatically right before you open a chosen app, and prompts you to revert them after.
Read this before you install anything

Geto does not hide Developer Options from one app while leaving it on for everything else. It scripts the real, system-wide toggle — flips the actual setting off right before launching your target app, and back on via a revert notification once you're done. It's convenience and automation, not true per-app spoofing.

It's also not guaranteed to work on every bank's app. Some banking apps have already been reported to detect this exact method. Treat it as "often works," not "guaranteed."

Setting it up

1 Install Shizuku or Brevent

Pick one — you only need one of the two:

  • Shizuku — needs a companion shell app (e.g. aShell) to actually run commands through it. Official download: shizuku.rikka.app/download ↗
  • Brevent — authorizes itself via a one-time ADB shell command. Official repo: github.com/brevent/Brevent ↗

Either one needs Developer Options turned on at least once for its own initial setup — Shizuku's wireless-debugging pairing, or Brevent's ADB authorization. That part is unavoidable; Geto's convenience only kicks in after this one-time step is done.

2 Install Geto from an official source

Geto requests a genuinely powerful permission — install it only from an official source, never a third-party APK mirror:

  • F-Droid (recommended) ↗
  • GitHub Releases ↗

Project home: github.com/JackEblan/Geto ↗ — check the releases page for whatever's newest rather than assuming a version pinned anywhere (including here) is current.

3 Grant Geto the permission it needs

Open Geto and try to add a rule. It'll prompt you with a command like this — run it through whichever tool you set up in step 1:

shell
pm grant com.android.geto android.permission.WRITE_SECURE_SETTINGS
  • Via Brevent: open its "Exec command" screen, paste the command, send it.
  • Via Shizuku: run it through a Shizuku-connected shell app (e.g. aShell).

A successful run shows exitcode=0. No visible output from pm grant itself is normal — silence means it worked.

Running Dual Space, a Work Profile, or a cloned app? Each Android user profile has independent permissions. If the app you're hiding settings from is cloned into a second profile, grant it there too:

shell — replace <profile_id>
pm grant --user <profile_id> com.android.geto android.permission.WRITE_SECURE_SETTINGS

Confirm both profiles are granted with:

shell
dumpsys package com.android.geto | grep WRITE_SECURE_SETTINGS

You should see one granted=true line per profile that actually needs it. A granted=false line for a profile you don't use for banking is harmless — ignore it.

4 Set up a rule for your banking app

Inside Geto, add your target app (e.g. your bank or e-wallet) and enable the toggles you want auto-hidden:

Setting keyLabel in GetoReliability
development_settings_enabledHide Developer OptionsWorks reliably
adb_enabledHide USB DebuggingWorks reliably
adb_wifi_enabledHide Wireless DebuggingWorks reliably
accessibility_enabledHide Accessibility ServicesInconsistent — some banks still detect it

Each enabled toggle flips off automatically when you launch the target app through Geto's shortcut, and Geto shows a revert notification to restore everything once you're done. Tap that notification before going back to XoDos-Ark — otherwise Developer Options stays off and your next install session will silently fail (see the Phantom Process Killer note above).

If a banking app still complains despite the Accessibility toggle being on, the more reliable fallback is manually turning off any Accessibility Service you actually have running, rather than relying on Geto to hide its "enabled" flag.

5 Undoing it, if you ever need to

Everything here is fully reversible — no bootloader, root, or system-partition changes anywhere in this process.

  • Revert an active hide: tap the revert notification, or re-enable the settings manually.
  • Revoke Geto's permission without uninstalling:
    shell
    pm revoke com.android.geto android.permission.WRITE_SECURE_SETTINGS
  • Remove Geto entirely: uninstall it normally — this removes the granted permission along with it, no manual cleanup needed.

A device restart does not undo the permission grant — permissions persist across reboots by design. A restart only resets whatever Geto had actively toggled mid-session back to its last real state.

L3 — PICKING YOUR COMBINATION

Choose your stack

XoDos-Ark lets you mix a distro, a desktop environment, and a display server. Not all combinations are equally proven.

LayerRecommendedWhy
DistroDebianLargest package availability, most predictable apt-based installer scripts, best-documented behavior in PRoot/Android contexts.
Desktop environmentXFCE4Lightest resource footprint of the commonly-available DEs, most consistently reported stable in PRoot setups.
Display serverX11Wayland typically needs direct DRM/KMS kernel access PRoot containers usually can't get — X11 via Termux-X11 is the traditional working path.

Everything else — other distros (Arch, Fedora, Ubuntu, Alpine…), other DEs (KDE, GNOME, LXQt, MATE, Cinnamon), or Wayland — should be treated as an optional fallback or experiment, not an equal alternative, unless you've already independently confirmed a specific combination works well on your own device. Heavier DEs like KDE Plasma or GNOME are realistically only viable on stronger devices — weigh your RAM and CPU tier before reaching for them.

Don't hardcode the options list

What's selectable inside XoDos-Ark's "Select Environment" and "Desktop Launchers" screens changes as the app updates. Open those screens yourself and use whatever's actually listed as current-truth for your session — not a screenshot from an old guide.

L4 — FRESH INSTALL WALKTHROUGH

Installing Debian + XFCE4 + X11

Each step below is a checkpoint — verify before moving to the next one. A broken step three parts in is much easier to fix than a broken desktop with no idea which part failed.

1 Confirm the fresh install is healthy

Open a terminal in your new Debian environment and run this whole block in one go — it runs six checks in sequence with labeled output:

bash
echo "### 1. Debian version/codename ###"; cat /etc/os-release; echo
echo "### 2. Architecture (should be arm64) ###"; dpkg --print-architecture; echo
echo "### 3. Package DB integrity ###"; apt-get check; echo
echo "### 4. Repo reachability ###"; apt update; echo
echo "### 5. Filesystem writable ###"; touch /root/.writetest && echo OK && rm /root/.writetest; echo
echo "### 6. Broken/leftover package state ###"; dpkg -l | grep -E '^.[^i]' | grep -v '^ii'; echo
echo "### Checks complete ###"

What "clean" looks like: (1) a real Debian codename, not silently older/newer than intended; (2) arm64; (3) no output; (4) completes with no Could not resolve, Connection failed, or Hash Sum mismatch — the single most important check, since a broken apt update causes confusing failures later; (5) OK; (6) nothing but header lines.

2 Confirm you're actually on X11, not Wayland

Do this before installing XFCE — a broken display target won't show up as an install error, it shows up later as "installed fine but nothing renders."

bash
echo $DISPLAY
echo $WAYLAND_DISPLAY
echo $XDG_SESSION_TYPE

$DISPLAY should show something like :0. $WAYLAND_DISPLAY should be empty. $XDG_SESSION_TYPE may say wayland even when X11 is genuinely running — this variable is commonly stale in PRoot containers. Don't trust it alone; use the authoritative test instead:

bash
apt install -y x11-utils
xdpyinfo | head -5

Real output (a vendor string like "The X.Org Foundation", screen info) means a genuine X11 server is responding. Error: unable to open display means nothing's listening — fix that before installing XFCE on top of it.

3 Optional: create a non-root user with sudo

XoDos-Ark's Debian container boots you in as root by default, and you can stay root the whole way through if you'd rather not deal with this. If you want a normal home directory and sudo instead:

bash — install sudo first, it's often missing on a minimal image
apt install -y sudo adduser
bash — replace <username> with your own
adduser <username>
usermod -aG sudo,audio,video,input,render <username>

Test it actually works before relying on it:

bash
su - <username>
sudo whoami

Should print root. If it hangs or fails instead: some PRoot filesystems mount nosuid, which blocks sudo/su elevation entirely — a known architectural limitation on some devices, not a mistake in the steps above. Test it directly rather than assuming either way. If it genuinely doesn't work, the fallback is simply staying root for install/config commands, while keeping the user account for its own home directory.

4 Install XFCE4

Use the XFCE install script from XoDos-Ark's "Desktop Launchers" screen for Debian. It should look close to this:

bash
apt-get update -y && apt-get upgrade -y
apt-get install -y --option Dpkg::Options::="--force-overwrite" xfce4 xfce4-goodies xfce4-whiskermenu-plugin mesa-utils xwayland libvulkan-dev mesa-vulkan-drivers libgl1-mesa-dri libglx-mesa0 libegl-mesa0 vulkan-tools dbus-x11 pulseaudio pavucontrol
export PULSE_SERVER=127.0.0.1
  • --force-overwrite is intentional — it resolves file-conflict clashes between the mesa GL/Vulkan packages. Not a red flag.
  • xwayland installs but won't be used on the X11 path — harmless, just extra disk space.
  • export PULSE_SERVER only applies inside this shell session. Add the same line to ~/.bashrc if you want working audio in future sessions.
5 Verify the XFCE install
bash
echo "### 1. No broken packages after forced install ###"; apt-get check; dpkg --audit; echo
echo "### 2. Core XFCE binaries present ###"; which startxfce4 xfce4-session xfwm4 xfce4-panel xfdesktop; echo
echo "### 3. No half-configured package state ###"; dpkg -l | grep -E '^.[^i]' | grep -v '^ii'; echo
echo "### 4. D-Bus session launcher ###"; dbus-launch --sh-syntax; echo
echo "### 5. Renderer check (GL + Vulkan) ###"; glxinfo -B | grep -i renderer; vulkaninfo --summary | grep -i deviceName; echo
echo "### Checks complete ###"

Clean output looks like: (1) both silent; (2) all five binaries resolve to a path; (3) nothing but header lines; (4) real DBUS_SESSION_BUS_ADDRESS= and DBUS_SESSION_BUS_PID= lines; (5) a software renderer — typically llvmpipe — reported on both GL and Vulkan. Hardware acceleration is not expected here; that's normal for PRoot containers on most devices, not a misconfiguration.

6 Pick the right launcher

XoDos-Ark usually lists two similar-looking XFCE launchers. Use "XFCE" (the one ending in exec dbus-run-session startxfce4), not "XFCE Desktop" (xfce4-session invoked directly). startxfce4 is the official entry point — it handles environment setup that the direct call skips.

7 First launch

Leave compositing at its default (on) the first time — don't change display settings before confirming things work normally. Drag a window or panel icon across the screen and watch for ghosting or trailing artifacts; it's a fast way to catch a compositor issue early, before installing more software on top. If everything renders cleanly and you just want a working Linux desktop, you can stop here.

8 Set up a coding environment

Git first, since everything else depends on it:

bash
apt install -y git curl wget

VS Code, arm64 build:

bash
wget -O vscode-arm64.deb "https://update.code.visualstudio.com/latest/linux-deb-arm64/stable"
apt install -y ./vscode-arm64.deb

Launch it with --no-sandbox — required, not optional:

bash
code --no-sandbox

PRoot filesystems commonly mount nosuid, which blocks the SUID-based sandbox Electron apps (VS Code, Chromium-based browsers) normally use. Without the flag, VS Code either fails to launch or crashes on startup — an architecture-level fact of PRoot containers generally, worth confirming rather than assuming. Make it permanent so you don't retype it every time:

bash
echo "alias code='code --no-sandbox'" >> ~/.bashrc

If you install a Progressive Web App through Chromium (the "Install App" browser menu option), the same nosuid issue applies — find its .desktop file and add --no-sandbox to the Exec= line the same way:

bash
grep -rn "Exec=" ~/.local/share/applications/*.desktop

Optional — GitHub CLI, if you'll be pushing to repos from here (choose HTTPS + a Personal Access Token when prompted, it avoids setting up SSH keys separately):

bash
apt install -y gh
gh auth login
L5 — STRUCTURAL, NOT DEVICE-SPECIFIC

Issues to watch for

These are facts about PRoot-on-Android as a category — true for any device or distro running under it, not one person's bug report. Watch for them proactively instead of being surprised.

CategoryWhat to watch forLimit
GPU / hardware accel PRoot containers have historically been blocked from directly accessing /dev/dri. Software rendering (llvmpipe for GL, lavapipe for Vulkan) is the reliable fallback. Newer driver-wrapper systems may improve this on some devices — verify, don't assume. Soft
Wayland Typically needs direct DRM/KMS kernel access PRoot containers usually can't get. X11 is the traditional working path. Soft
D-Bus / systemd PRoot environments typically lack a running system D-Bus and systemd. Desktop environments often need a manual dbus-launch step and explicit session variables before the GUI renders properly. Soft — expected workaround
sudo / su elevation Some PRoot filesystems mount nosuid, blocking sudo/su and SUID-sandboxed apps (Chromium, Electron). Workaround: --no-sandbox flags, or operate as root directly. Soft
musl vs. glibc Distros using musl libc (Alpine, Chimera, Adelie) may fail to run glibc-compiled binaries like Chromium or VS Code, even with sandbox flags fixed. Hard — generally not fixable without musl-compiled alternatives
systemd-less distros Don't assume "no systemd" (Artix, Void, etc.) is automatically better for a stripped-down container — it may just mean less precedent for working around PRoot's already-limited init/D-Bus environment. Untested — verify, don't infer
Installer scripts DE installer scripts inside XoDos-Ark are generated per-distro. Package names and bundled fixes vary between distro families — review the actual script before running it. Practice, not a bug
Confidence levels aren't all equal

When you're getting advice — from a guide, a classmate, or an AI — separate three tiers: a confirmed, tested pairing in a PRoot/Android context; something likely to work based on general Linux knowledge but untested here; and a named risk like the musl/glibc mismatch above — a real, foreseeable problem, not a guess. Advice that presents all three with the same confidence is worth double-checking.

L6 — WHEN SOMETHING BREAKS

Getting unstuck

PRoot-on-Android has enough quirks that you will eventually hit something not covered above. AI assistants are genuinely capable at this kind of troubleshooting — but only with enough context.

  • Paste the exact error output, not a summary. "It's not working" gives almost nothing to work with. The literal error text — copy-pasted, not retyped from memory — usually contains the specific clue.
  • State your full stack up front: device, distro, DE, display server, XoDos-Ark version — especially in a fresh conversation with no memory of prior context.
  • Say this is a PRoot container on Android, not a normal Linux install. A fix that works on bare-metal Linux can be flatly impossible under PRoot.
  • Try one suggested fix at a time. If given three possible causes, test them one at a time — otherwise, if something works, there's no way to know which change actually fixed it.
  • If a fix doesn't work, say so and paste the new output, rather than restarting the conversation from scratch. The follow-up error is usually more specific and gets to a real fix faster.

Any capable AI can help here — Claude, ChatGPT, DeepSeek, Gemini, or others. If an answer sounds too confident about something clearly untested, it's reasonable to cross-check with a second AI or just ask it directly how confident it actually is, and why.
